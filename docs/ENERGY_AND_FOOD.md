# 饮食估算与训练热量

## 数据和授权

备忘录授权独立保存，旧配置默认关闭。开启后提取最多 20 条未删除备忘录，每条标题最多 100 个字符、正文最多 1000 个 Unicode 码点，不遍历回收站。关闭时不查询备忘录。普通聊天上下文不会自动包含食物照片。

按名称估算只发送本次食物描述，不附带备忘录、档案或其他页面的数据。照片使用系统拍照/选图界面；支持 JPEG、PNG、WebP，最多 5 MB，移动端选择时限制至约 1280 像素并压缩。照片先预览，再展示用户已配置的 API 主机与图片模型，点击「发送并估算」才上传。取消不发送；识别结果不自动入库，用户仍需保存饮食记录。编辑描述后到达的旧请求不会覆盖新内容。Android 相机意外回收后的结果可在重新打开饮食表单时尝试恢复，恢复后仍需确认发送。

图片模型可与聊天模型分别设置，调用同一个用户配置的兼容接口。默认沿用聊天模型；服务商或模型不支持图片时展示错误并提示配置图片模型。没有使用应用作者的共享密钥，也没有调用用户密钥进行本次开发测试。

## 食物估算

配置并启用 AI 后，可输入食物名称、份量及做法，由模型给出总热量、可选营养素与估算假设。返回数据必须包含可识别食物和有效热量，异常、不完整结果不能直接写入。没有 AI 时仅对少量常见单一食物使用内置粗略能量参考，不把复杂菜名中的单个词当成整道菜。

离线参考不是权威营养数据库，做法、可食部、含水量、配方和用油会明显影响结果。优先使用包装营养标签或实测份量；可参考 [USDA FoodData Central](https://fdc.nal.usda.gov/) 查询具体食物。照片中的体积、重量、油盐和被遮挡的食材都不能保证识别准确。

## 消耗口径

基础日常消耗沿用 [Mifflin–St Jeor 成人公式](https://pubmed.ncbi.nlm.nih.gov/2305711/) 与档案中的日常活动系数。日常活动设置应排除另行记录的训练，避免重复计算；历史日期的日常消耗仍按当前档案估算，不构成当时的测量值。

训练参考 [2024 Adult Compendium 的活动分类](https://pacompendium.com/conditioning-exercise/)，按体重与活动时长估算。净运动消耗扣除 1 MET 静息部分，再计入日常消耗。普通抗阻训练参考 3.5 MET，部分大负重复合动作使用较高强度分类；负重相对体重的阈值属于应用的粗略强度代理，不是已验证的个体热量预测模型。不能将「重量 × 次数」直接解释成准确消耗。

优先使用填写的总训练时长；计时训练可使用真实经过时长；无时长时按每次约 3 秒、组间约 60 秒粗估，休息使用低强度活动假设。跑步、骑行、步行使用相应的概略活动强度，不能反映实际速度和坡度。展示的整数千卡仅便于记录，不表示这种精度的测量能力。

只有已完成的训练计入当日消耗。保存时保留估算热量、档案体重和估算时长，后续改变体重不重算历史训练。旧数据缺少这些字段时保留为空，页面提示没有计入；不默认假设 65kg。手动补记不伪造开始结束区间，避免影响原有真实专注/训练时长统计。训练计划预设值会带入记录表单，用户需根据实际情况修改后点击完成。

## 每日比较与建议

全天预计消耗 = 当前档案的日常消耗 + 当日已完成训练的估计净消耗。摄入只汇总保存且填写了热量的饮食。没有记录或热量漏填时不计算完整差额；今天尚未结束时明确提示这是目前摄入与全天估计的比较，不据此要求少吃或补偿运动。建议鼓励核对漏记并观察多日趋势。成人估算不能作为未成年人、孕期/哺乳期或特殊疾病人群的个体化处方，可参考 [NIDDK 的体重管理说明](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner)。

## 图标与 DDL

Windows 在通知初始化前刷新自己的开始菜单通知快捷方式、可执行路径、版本化图标路径及 AppUserModelId 图标注册；不清空全系统图标缓存。Android 通知继续遵循系统单色图标规范，用勾选与格线代替旧的通用铃铛。

DDL 仍使用原来的任务与截止日期数据，不迁移成每日习惯。查询从创建日期起保留未完成 DDL，逾期在待处理列表标注；完成日仍可查看，从之后日期收起，历史日期根据完成时刻显示状态。

## 验证范围

自动化测试覆盖照片的多模态请求、图片模型选择、无授权/无配置不发送、返回数据检查、名称离线估算、热量计算、备忘录授权及回收站排除、跨日 DDL、训练保存与备份字段，以及 320px 手机表单和身体档案卡布局。照片实际识别质量取决于用户配置的模型，开发验证使用模拟响应，没有以用户 API Key 调用真实识图服务；拍照硬件和各品牌系统权限仍需真机验证。

完整 Flutter 回归 245 项通过，另验证训练保存后常驻饮食页面的消耗立即更新。全项目静态检查无错误。Windows 原生通知身份代码已通过发布构建；Android 拍照依赖在本机 C/D 跨盘环境禁用 Kotlin 增量缓存以避免构建路径错误。实际照片识别、相机硬件与通知外观未以用户真机和真实服务进行端到端验证。

Windows 通知内部标识使用不含空格的 Dayloom，展示名称单独注册为「拾序 · Dayloom」，以满足 [Microsoft AppUserModelID 规范](https://learn.microsoft.com/zh-cn/windows/win32/shell/appids)。local_notifier 把 appName 同时用作内部标识，因此不能直接用带空格的完整展示名。
